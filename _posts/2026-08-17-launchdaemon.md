# Запуск сервисов на Mac в режиме LaunchDaemon. Часть 1

## Введение

Если вы разворачиваете на Mac что-то полезное — прокси, агента мониторинга, бэкап-скрипт или базу данных — рано или поздно понадобится, чтобы процесс стартовал сам при загрузке системы и не умирал после сбоев. На macOS управлением фоновыми процессами занимается **launchd** — системный демон, который становится первым процессом в системе и родительским для всех остальных.

В этой статье разберём, как правильно настроить **LaunchDaemon** — системный сервис, который запускается при загрузке, до входа пользователя, и по умолчанию работает с правами root.

## LaunchDaemon и LaunchAgent

В macOS launchd управляет двумя типами сервисов. Разница между ними определяет, где лежит конфигурация и от чьего имени работает процесс.

**LaunchDaemon** — системный сервис:

- конфигурация лежит в `/Library/LaunchDaemons` (для своих сервисов; каталог `/System/Library/LaunchDaemons` — системные сервисы Apple, трогать его не стоит);
- загружается при загрузке системы, **до входа любого пользователя**;
- по умолчанию работает от имени **root**;
- подходит для сервисов, которые нужны всей машине: сеть, базы данных, мониторинг, системные утилиты.

**LaunchAgent** — пользовательский сервис:

- лежит в `~/Library/LaunchAgents` (для конкретного пользователя) или `/Library/LaunchAgents` (для всех пользователей);
- загружается **при входе пользователя**;
- работает с правами этого пользователя;
- подходит для фоновых приложений, которым нужна сессия пользователя: мессенджеры, синхронизация, клиентские агенты.

| Критерий           | LaunchDaemon             | LaunchAgent              |
| ------------------ | ------------------------ | ------------------------ |
| Каталог            | `/Library/LaunchDaemons` | `~/Library/LaunchAgents` |
| Момент запуска     | при загрузке системы     | при входе пользователя   |
| Права по умолчанию | root                     | текущий пользователь     |
| Видимость          | весь компьютер           | только пользователь      |

Правило выбора простое: нужен сервис до входа пользователя и с правами root — это LaunchDaemon, нужен «в фоне у пользователя» — LaunchAgent.

## Структура plist-файла

Настройка LaunchDaemon — это XML-файл в формате plist, который кладётся в `/Library/LaunchDaemons`. Минимальный рабочий пример:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.example.myservice</string>

    <key>ProgramArguments</key>
    <array>
        <string>/usr/local/bin/myservice</string>
        <string>--config</string>
        <string>/etc/myservice/config.yml</string>
    </array>

    <key>WorkingDirectory</key>
    <string>/usr/local/bin</string>

    <key>RunAtLoad</key>
    <true/>

    <key>KeepAlive</key>
    <true/>

    <key>StandardOutPath</key>
    <string>/var/log/myservice.out.log</string>
    <key>StandardErrorPath</key>
    <string>/var/log/myservice.err.log</string>
</dict>
</plist>
```

Разберём ключевые параметры:

- **`Label`** — уникальный идентификатор сервиса. По конвенции используется обратный домен (`com.example.myservice`). По этому имени launchd управляет сервисом, дубликаты недопустимы.
- **`ProgramArguments`** — массив: первый элемент — путь к исполняемому файлу, остальные — аргументы. Есть упрощённый вариант `Program` (одна строка), но `ProgramArguments` — основной способ.
- **`WorkingDirectory`** — рабочий каталог процесса. Важно, если сервис использует относительные пути.
- **`RunAtLoad`** — запускать ли сервис сразу после загрузки конфигурации. Для большинства демонов — `true`.
- **`KeepAlive`** — перезапускать ли сервис, если он завершился. Значение `true` означает «перезапускать всегда», но можно задать и условия (например, только при ненулевом коде выхода).
- **`StandardOutPath` / `StandardErrorPath`** — куда писать stdout и stderr. Без этих ключей вывод теряется, и отладка превращается в угадывание.

Дополнительно полезны `EnvironmentVariables` (переменные окружения), `StartInterval` (запуск по таймеру) и `StartCalendarInterval` (по расписанию, аналог cron), но для типового демона достаточно приведённого выше набора.

## Установка демона

Сам файл plist нужно оформить по правилам: владелец `root`, группа `wheel`, права `644`. launchd откажется загружать файл с «чужими» правами.

```bash
sudo chown root:wheel /Library/LaunchDaemons/com.example.myservice.plist
sudo chmod 644 /Library/LaunchDaemons/com.example.myservice.plist
```

Дальше — регистрация в launchd. Современный способ (macOS 10.10 и новее) — команда `bootstrap`:

```bash
sudo launchctl bootstrap system /Library/LaunchDaemons/com.example.myservice.plist
```

Удалить сервис обратно:

```bash
sudo launchctl bootout system /Library/LaunchDaemons/com.example.myservice.plist
```

Команды `launchctl load` / `unload` — устаревший вариант: они всё ещё работают, но Apple их не рекомендует, и на новых версиях macOS могут вести себя не так, как ожидается.

Проверить, что сервис загружен и работает:

```bash
launchctl print system/com.example.myservice
```

Команда `print` выводит состояние сервиса: PID, код последнего завершения, счётчики перезапусков, параметры. Это основной инструмент для проверки «а жив ли мой демон».

## Частые ошибки на старте

1. **Неверный Label.** Если label уже занят другим сервисом, `bootstrap` завершится с ошибкой. Проверьте занятость: `launchctl print system`.
2. **Неверные права на plist.** Файл должен принадлежать `root:wheel` и иметь права `644`.
3. **Относительные пути.** launchd запускает процесс с минимальным окружением: нет `PATH` из вашей shell. Всегда указывайте **абсолютные** пути к исполняемому файлу и конфигурации.
4. **Ошибки валидации plist.** Перед загрузкой проверьте файл: `plutil -lint /Library/LaunchDaemons/com.example.myservice.plist`.
5. **SIP (System Integrity Protection).** Системные каталоги (`/usr`, `/bin`, `/sbin`) защищены — туда записать бинарь root'ом не получится. Ставьте свои программы в `/usr/local/bin` или в `/opt`.

Часть 1 закончилась на том, что сервис зарегистрирован и работает. Теперь разберём, как управлять им, читать логи и разбираться в сбоях.

## Управление работающим сервисом

Все команды управления работают через `launchctl` и используют домен `system` для LaunchDaemon.

| Команда                                               | Что делает                                          |
| ----------------------------------------------------- | --------------------------------------------------- |
| `launchctl print system/com.example.myservice`        | Состояние: PID, код выхода, счётчики перезапусков   |
| `launchctl kickstart -k system/com.example.myservice` | Перезапуск: SIGKILL текущему процессу и новый старт |
| `launchctl kickstart system/com.example.myservice`    | Запустить, только если сейчас не запущен            |
| `launchctl stop system/com.example.myservice`         | Остановить (SIGTERM, с ожиданием)                   |
| `launchctl bootout system/com.example.myservice`      | Выгрузить сервис из launchd                         |
| `launchctl enable system/com.example.myservice`       | Включить автозагрузку (переживает перезагрузку)     |
| `launchctl disable system/com.example.myservice`      | Отключить автозагрузку                              |

Несколько нюансов:

- **`kickstart -k`** — самый быстрый способ «перезапустить демон». Без флага `-k` команда ничего не сделает, если процесс уже работает.
- **`stop`** останавливает сервис, и `KeepAlive` его не поднимет обратно — остановка не считается сбоем. Чтобы запустить снова: `kickstart` без `-k`.
- **`disable`** — «выключатель» на уровне launchd: после него `bootstrap` не запустит сервис, даже если plist лежит на месте. Часто помогает при отладке «зависшего» демона: `disable` → починить → `enable` → `bootstrap`.
- **Важно:** изменения в plist **не подхватываются** ни `kickstart`, ни `print`. Чтобы применить правки конфига — полный цикл `bootout` + `bootstrap`.

Проверить список всех системных сервисов:

```bash
launchctl list | grep myservice
launchctl print system
```

## Перезапуск при сбое: KeepAlive подробнее

В части 1 мы задали `KeepAlive` значением `true` — «перезапускать всегда». Но у ключа есть и более тонкие варианты:

```xml
<!-- Перезапускать только если процесс завершился с ненулевым кодом -->
<key>KeepAlive</key>
<dict>
    <key>SuccessfulExit</key>
    <false/>
</dict>
```

```xml
<!-- Перезапускать при появлении сети -->
<key>KeepAlive</key>
<dict>
    <key>NetworkState</key>
    <true/>
</dict>
```

Для «всегда живого» демона `true` — правильный выбор, а `SuccessfulExit` полезен, если сервис завершает работу осознанно (например, после обновления конфигурации) и не должен перезапускаться сам.

Два связанных ключа:

- **`ThrottleInterval`** — минимальный интервал между перезапусками в секундах (по умолчанию 10). Если бинарь падает сразу после старта, launchd будет перезапускать его не чаще, чем раз в этот интервал. При отладке «бесконечного цикла падений» это видно в `launchctl print` — счётчик перезапусков растёт, а PID не меняется надолго.
- **`ExitTimeOut`** — сколько секунд launchd ждёт корректного завершения после SIGTERM перед SIGKILL. Полезно для сервисов, которые прилично завершаются (закрывают соединения, дописывают данные).

И главное правило: **программа не должна демонизироваться сама**. Если бинарь делает двойной fork и уходит в фон, launchd считает, что процесс завершился, — и с `KeepAlive` это превращается в бесконечный цикл «запустил — «умер» — запустил». Запускаемый бинарь обязан жить в первом плане.

## Логирование

launchd не умеет ротацию логов, и всё, что нужно, — это `StandardOutPath` и `StandardErrorPath` из части 1. Но есть нюансы.

1. **Файлы создаёт launchd**, но только если каталог уже существует. Поставили лог в несуществующий `/var/log/myservice/` — сервис не запустится, а в логах будет «couldn't be started: No such file or directory».

2. **launchd держит файловые дескрипторы открытыми** на всё время жизни процесса. Если вы используете `logrotate` с обычной ротацией (переименование файла), процесс продолжит писать в переименованный файл. Рабочие варианты:
   - `copytruncate` в logrotate (копируем содержимое и обрезаем файл) — самый простой;
   - перезапуск сервиса после ротации (`kickstart -k`);
   - правильнее всего: логирование реализовать в самом приложении (собственная ротация или запись в `syslog`/unified logging).

3. **Права на лог-файлы.** Файл создаётся от имени того пользователя, под которым работает сервис (для демона — root). Если сервис работает от `User` (см. часть 3), убедитесь, что он может писать в лог.

4. **Unified logging.** Вывод в файлы — основной способ, но системные события вокруг сервиса (запуск, остановка, ошибки загрузки) видны в journal-подобной системе macOS:

   ```bash
   log show --last 1h --predicate 'process == "launchd"' --info
   log stream --predicate 'subsystem == "com.apple.xpc.launchd"'
   ```

   Удобно, когда в `StandardErrorPath` пусто, а сервис «не стартует».

5. **Практика.** Разделяйте `.out` и `.err`, кладите логи в `/var/log/<имя-сервиса>/` и делайте этот каталог частью деплоя. Если приложение умеет писать в stderr по умолчанию — достаточно одного `StandardErrorPath`.

## Отладка: пошаговый порядок

Когда сервис не стартует или падает, действуйте в таком порядке:

**Шаг 1. Валидация plist.**

```bash
plutil -lint /Library/LaunchDaemons/com.example.myservice.plist
```

Ломает XML или опечатка в ключе — `bootstrap` не скажет ничего вразумительного, а `plutil` укажет на строку.

**Шаг 2. Состояние в launchd.**

```bash
launchctl print system/com.example.myservice
```

Смотрите три вещи: `state` (running / exited / spawn), `last exit code`, `pid`. Код выхода — первый источник диагноза:

| Код | Значение                        | Что делать                                  |
| --- | ------------------------------- | ------------------------------------------- |
| 0   | нормальное завершение           | если не ожидали — проверьте логи приложения |
| 78  | ошибка конфигурации (EX_CONFIG) | приложение не смогло прочитать конфиг       |
| 126 | файл найден, но не исполняемый  | `chmod +x`, права                           |
| 127 | файл не найден                  | абсолютный путь, SIP                        |
| 137 | SIGKILL (128 + 9)               | чаще всего OOM-killer или ручной `kill -9`  |

**Шаг 3. Запустить вручную.** launchd запускает процесс с минимальным окружением, поэтому «у меня в терминале работает» — не аргумент. Запустите так же, как launchd:

```bash
sudo -u root env -i /usr/local/bin/myservice --config /etc/myservice/config.yml
```

`env -i` очищает окружение до состояния, близкого к launchd. Если падает — причина в окружении; если работает — смотрите логи.

**Шаг 4. Лог stderr.** Частые находки: «permission denied» на конфиг, «address already in use» (порт занят другим процессом — `lsof -i :<порт>`), «no such file» (относительные пути).

**Шаг 5. Крэш-репорты.** Если процесс падает с сигналом (SIGSEGV, SIGABRT), macOS пишет отчёт:

```bash
ls -t /Library/Logs/DiagnosticReports/ | head
```

**Шаг 6. Быстрый тест без файла.** Чтобы проверить команду, не трогая plist, можно подать задание прямо в командной строке:

```bash
sudo launchctl submit -l com.example.test -- /bin/echo "hello from launchd"
sudo launchctl print system/com.example.test
sudo launchctl remove system/com.example.test
```

Отдельно про окружение: у launchd-демона нет вашего `PATH`, `HOME` для root равен `/`. Если бинарь ищет что-то относительно `$HOME` или зависит от `PATH` — задайте явно:

```xml
<key>EnvironmentVariables</key>
<dict>
    <key>PATH</key>
    <string>/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin</string>
    <key>MY_CONFIG</key>
    <string>/etc/myservice/config.yml</string>
</dict>
```

# Запуск сервисов на Mac в режиме LaunchDaemon. Часть 3

В первой части мы развернули сервис, во второй — научились управлять им и отлаживать. Завершаем статью типовыми сценариями, вопросами безопасности и итоговым чек-листом.

## Типовой сценарий 1: периодический запуск по расписанию

LaunchDaemon — не только «вечно живой демон». Если сервис нужен не постоянно, а по расписанию (бэкапы, очистка, синхронизация), LaunchDaemon заменяет cron целиком.

**Каждые N секунд** — ключ `StartInterval`:

```xml
<key>StartInterval</key>
<integer>300</integer>
```

Сервис будет запускаться каждые 300 секунд. Если процесс ещё работает, запуск не дублируется. `KeepAlive` здесь не нужен — и его ставить не стоит, иначе сервис не даст себе закончиться.

**По расписанию** — `StartCalendarInterval`, аналог cron, но мощнее:

```xml
<key>StartCalendarInterval</key>
<array>
    <dict>
        <key>Hour</key>
        <integer>3</integer>
        <key>Minute</key>
        <integer>15</integer>
    </dict>
</array>
```

Массив позволяет задать несколько срабатываний. Доступны ключи `Minute`, `Hour`, `Day`, `Weekday`, `Month`. Комбинации работают как в cron: `Weekday 0` + `Hour 3` — каждое воскресенье в 3 часа. Важное отличие от cron: если Mac спал в момент срабатывания, launchd запустит задание при пробуждении — «упущенный» бэкап не потеряется.

**По событию** — `WatchPaths` и `QueueDirectories`: запуск при изменении файлов или появлении элементов в очереди. Удобно для «обработчиков» входящих данных.

## Типовой сценарий 2: порядок запуска и зависимости

Иногда сервис зависит от другого (например, агент мониторинга ждёт, пока поднимется база данных). launchd умеет выражать зависимости, но осторожно:

```xml
<key>KeepAlive</key>
<dict>
    <key>PathState</key>
    <string>/var/run/myservice/ready</string>
</dict>
```

Вариант `PathState` — сервис будет перезапускаться, когда появится (или исчезнет) указанный файл. Простой и надёжный способ выразить «жду, пока другая подсистема будет готова»: зависимый сервис создаёт файл-флаг, а наш демон ждёт его.

Альтернатива — `WatchPaths`: сервис стартует, когда файл появляется. Альтернатива альтернативы — просто сделать бинарь устойчивым к отсутствию зависимости (переподключение, повторные попытки), что в distributed-системах обычно надёжнее «идеального порядка запуска».

## Типовой сценарий 3: обновление и снятие с эксплуатации

Обновление уже работающего демона — стандартный цикл:

```bash
# 1. Выгрузить старую конфигурацию
sudo launchctl bootout system/com.example.myservice
# 2. Обновить бинарь и конфиг
# 3. Загрузить новую
sudo launchctl bootstrap system /Library/LaunchDaemons/com.example.myservice.plist
```

Если сервис «застрял» (не отвечает на SIGTERM, `stop` завис):

```bash
sudo launchctl kickstart -k system/com.example.myservice
# или, если даже это не помогло:
sudo launchctl bootout system/com.example.myservice
sudo launchctl enable system/com.example.myservice
sudo launchctl bootstrap system /Library/LaunchDaemons/com.example.myservice.plist
```

Полное снятие с эксплуатации — симметричный порядок:

```bash
sudo launchctl bootout system/com.example.myservice
sudo rm /Library/LaunchDaemons/com.example.myservice.plist
```

## Безопасность

LaunchDaemon работает от имени root — это сила и одновременно риск. Несколько принципов:

1. **Принцип минимальных привилегий.** Если сервису не нужны права root, укажите `User` и `Group` в plist:

   ```xml
   <key>User</key>
   <string>myservice</string>
   <key>Group</key>
   <string>myservice</string>
   ```

   Создайте отдельного пользователя (`sudo dscl . -create /Users/myservice UniqueID 501`) и давайте ему доступ только к необходимым ресурсам. Компрометация такого демона не даст root.

2. **Не запускайте интерпретаторы скриптов.** Типичная ошибка — делать бинарь демона `bash -c "..."` или `python script.py` с правами root. Любая уязвимость в скрипте (RCE, подмена конфигурации) сразу даёт root. Оберните логику в отдельный бинарь с понятными правами.

3. **Конфиги — как бинарники.** Файлы конфигурации демона должны быть `root:wheel 640` (или `600`), если в них есть секреты. Записываемые другим процессом конфиги демона root — это вектор атаки: процесс с меньшими правами может подменить конфиг и повлиять на демона.

4. **Логи не должны содержать секреты.** `StandardOutPath` читается тем, кому вы дали права. Не печатайте пароли, токены и ключи в stdout/stderr демона.

5. **Каталог `/Library/LaunchDaemons`** доступен только root — это защита от того, что любой локальный пользователь положит туда свой plist. Но если на машине есть другие пользователи с sudo — они могут установить любой демон. На серверах это штатно, но на рабочих станциях стоит держать в уме.

6. **SIP и sandbox.** Для системных функций, где возможно, используйте `Sandbox` в plist (macOS поддерживает sandbox-профили для launchd-сервисов) — это дополнительно ограничит демона.

7. **Проверяйте, что запускаете.** Перед `bootstrap` перечитайте `ProgramArguments`: опечатка в аргументе или подмена бинаря в `/usr/local/bin` — это тоже атаки. Фиксируйте бинарники в CI/CD, подписывайте их (codesign) и проверяйте целостность.

## Итоговый чек-лист

Перед деплоем нового LaunchDaemon пройдитесь по списку:

- [ ] `Label` уникален, по конвенции обратного домена.
- [ ] `ProgramArguments` — абсолютные пути, бинарь исполняемый.
- [ ] Права на plist: `root:wheel 644`.
- [ ] `plutil -lint` прошёл без ошибок.
- [ ] `RunAtLoad` = `true` (если сервис нужен сразу).
- [ ] `KeepAlive` настроен осознанно: `true` для демонов, условия для периодических задач.
- [ ] `StandardOutPath` / `StandardErrorPath` заданы, каталог для логов существует.
- [ ] `EnvironmentVariables` заданы, если сервис зависит от окружения.
- [ ] Сервис не демонирует сам (нет двойного fork).
- [ ] Права минимальны: `User`/`Group` заданы, если root не нужен.
- [ ] Конфиги с секретами защищены (`600`/`640`).
- [ ] Проверено `launchctl print system/<label>` после `bootstrap`.
- [ ] Проверено, что сервис переживает перезагрузку (`sudo reboot`, потом `launchctl print`).
- [ ] Есть процедура обновления (`bootout` → обновить → `bootstrap`) и снятия с эксплуатации.

## Заключение

LaunchDaemon — это надёжный, предсказуемый и не слишком сложный способ держать сервисы на macOS: системный запуск до входа пользователя, перезапуск при сбоях, расписание вместо cron и единый инструмент управления через `launchctl`. Главное — помнить правила: абсолютные пути, `root:wheel 644` на plist, `bootstrap`/`bootout` вместо устаревших `load`/`unload`, отдельный пользователь, если root не нужен, и осознанный `KeepAlive`.

Собрав эти привычки, вы получите сервисы, которые переживают перезагрузки, сбои и обновления — без ручного вмешательства.
